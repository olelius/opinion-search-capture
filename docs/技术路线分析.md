# 技术路线分析：双平台关键词截图与动态导出

日期：2026-09-08。状态：技术分析原稿，已据此进入首版开发；手机端使用Android模拟器且不依赖真机。最新实测与开发边界见 `docs/首轮验证与开发交接.md`，下文中的PoC计划不等同于全部已通过。

## 1. 已确认事实与分析边界

- 用户要求小红书、B站，各自覆盖手机端/网页端的搜索 TOP N 与下拉词，共 8 种采集组合；N 默认 20，支持配置，多关键词。
- 用户要求每日 9—21 时及自定义时间段，原图与拼图的目录、文件名由固定文本和字段组合，字段精确匹配。
- 本地资料本轮复核为 116 张 JPG；查看了四张 SEO 拼图和搜索结果/下拉词代表性单图。原始截图保持不变。
- 搜索结果参考图是长图，不是“20 张单独的帖子详情截图”。B站代表图为 1080×12281，小红书代表图为 1080×9456；目录名 TOP20 并不能证明图片严格包含 20 条有效结果。
- 搜索结果拼图采用多关键词长图横向排列；下拉词拼图采用多列、两行排列。已查看样例有手机状态栏及 App 式界面；本轮未取得这些图的原始采集流程。
- 当前没有 WEB 截图参考，也未实测两个平台当前登录态、控件树、网页 DOM、分页和滚动行为。工具文档证明基础能力，不证明平台适配成功率。
- 当前按“Windows 本地管理、Android 模拟器内运行原生 App”比较方案；用户明确测试也不使用真机，不再把真机列为验证前提。多人远程管理仍属待确认分支。

## 2. 语言和技术建议

### 推荐组合

| 模块 | 首版建议 | 原因与边界 |
| --- | --- | --- |
| 主语言 | Python | 统一设备控制、网页自动化、图像处理、任务调度和本地文件操作；主要耗时预计在页面加载和设备操作，需实测 |
| 本地管理界面 | PySide6 Widgets | 适合关键词表、时间配置、目录选择、模板预览、任务列表；界面与采集核心分离 |
| 网页采集 | Playwright Python + Chromium | 操作实际网页，读取 DOM、等待页面就绪、保留独立会话并截图；两个平台独立适配 |
| Android 手机采集 | openatx/uiautomator2 + ADB + Android 模拟器 | 根据控件定位、输入、滑动、取屏；首轮比较雷电/MuMu，AVD作为标准化备选；平台兼容性待实测 |
| 图像处理 | Pillow；滚动对齐按需引入 OpenCV | Pillow 负责排版、缩放、保存；OpenCV 辅助重叠区域对齐，不替代业务条目识别 |
| 定时与状态 | APScheduler + SQLite | 调度器发出触发事件，数据库记录业务批次、子任务、重试和产物；避免只靠内存定时器 |
| 模板 | 白名单字段解析器 + pathlib | 固定文本、类型化字段和有限格式化；不执行用户表达式，不把文件名当数据来源 |
| 分发 | PyInstaller onedir | 先用目录式 EXE，单独管理浏览器、ADB、设备端依赖；打包后仍需在目标机验证 |

PySide6 是 Qt 官方 Python 绑定；Playwright 支持页面、整页和元素截图；uiautomator2 提供设备截图和控件树读取。来源：[Qt for Python](https://doc.qt.io/qtforpython-6/)、[Playwright 截图](https://playwright.dev/python/docs/screenshots)、[uiautomator2](https://github.com/openatx/uiautomator2)。

### 与其他路线比较

- **Python + PySide6：优先推荐。** 在当前本地文件导出、连接手机的假设下，运行组件较少，界面和采集共用一种语言。
- **React/TypeScript + FastAPI + Python 采集核心：多人或远程管理时推荐。** 管理界面经浏览器访问，但手机控制仍需要设备旁的执行程序；增加前后端通信、服务部署和账号管理成本。若首版就需要多用户，应从此路线起步。
- **Electron/TypeScript + Playwright + Appium：可行。** 对网页界面开发熟悉的团队有优势，但原生手机操作仍需移动自动化驱动；不会因全用 TypeScript 就消除设备或平台适配难点。
- **纯 requests/Scrapy：不作为截图主链路。** 数据响应不等于用户看到的真实页面；重新渲染页面也不是原页面截图。
- **纯鼠标坐标或图像点击脚本：不作为主链路。** 窗口、缩放、弹窗、控件变化会影响动作；坐标/OCR 仅在局部控件不足时辅助。
- **Appium 是另一种设备驱动选择，不与 openatx/uiautomator2 默认叠加。** Android 单机首版优先轻量的 Python 封装；若要统一多种移动系统或已有 Appium 基础，再选 Appium 驱动体系。[Appium 驱动说明](https://appium.io/docs/en/latest/intro/drivers/)

版本在 PoC 通过后锁定，不在没有依赖验证的阶段凭“最新”指定组合。当前 APScheduler 设计可参考 [3.x 用户指南](https://apscheduler.readthedocs.io/en/3.x/userguide.html)，不混用不同大版本 API。

2026-09-08 补充：已完成无真机路线的GitHub调研，见 `docs/模拟器与App截图GitHub调研.md`。APP默认采用视觉滚动截屏：图像重叠负责长图几何，必要的可见卡片计数负责TOP N边界；`strict_evidence`作为需要更强身份/封面证据时的可选模式。uiautomator2默认截图路径在本轮核查代码中使用JPEG质量80，正式清晰原图采用ADB PNG路径。

## 3. 手机端与网页端应分离

Playwright 的手机模拟设置调整的是浏览器的视口、User-Agent、触摸等行为，不会把网页转换成原生 App。手机 H5 与 App 应使用不同来源标签和验收标准。[Playwright 设备模拟](https://playwright.dev/python/docs/emulation)

- 手机端按 Android 模拟器内的原生 App 做技术验证，开发和测试都不依赖真机。模拟器运行真实 App 界面，区别于浏览器调整手机视口；结果记录为 Android 模拟器环境观测，不宣称代表所有真实手机的统一排名。
- 若未来增加 iPhone，另立兼容性范围；不纳入当前无真机的 Android 路线。XCUITest 官方主要要求 macOS、Xcode、Appium，非 macOS 仅有限支持。[XCUITest 系统要求](https://appium.github.io/appium-xcuitest-driver/latest/getting-started/system-requirements/)
- 一个手机设备上的两个 App 共享前台界面，操作串行；不同设备及隔离浏览器资源按实测允许并行。同一浏览器页面或独占配置目录也应互斥。
- 用户通过名称选择设备/会话，内部保存稳定标识，不要求用户记设备 ID。
- 登录失效、验证码、断连或异常弹窗进入暂停/失败状态，记录现场并提示处理；不将异常页标记为有效截图。
- 会话数据仅本地保留，与导出图片和 Git 分离；可复用登录态不代表会话永远有效。[Playwright 登录态](https://playwright.dev/python/docs/auth)

建议 4 个平台端适配器：小红书 APP、小红书 WEB、B站 APP、B站 WEB；每个实现搜索结果、下拉词两种动作。调度、命名、拼图和状态管理共用。

## 4. TOP N 和两层拼接

### TOP N 先定义统计口径

样例中存在用户/账号模块、相关搜索、大家都在搜及内容卡片。需要确认：

1. 默认“综合”还是“最新”等排序；是否保留固定筛选、登录会话和设备配置。
2. N 统计视频/笔记内容，还是包括广告、用户卡、推荐模块。建议内容条目计数，插入模块另记；是否计入广告需明确。
3. 多列瀑布流按何种顺序判定排名；DOM/控件顺序与视觉顺序需核对，避免“滚动若干屏＝20条”。
4. 少于 N 条时，实际记录条数并显示“不足 N”，不补入后续时段内容。
5. 邻列卡片高度不等时，覆盖第 N 条可能同时带入第 N+1 条的局部画面；保留原始界面，在派生说明中标明有效排名范围，严格裁切规则需验收。

**第一层：同关键词长图。** 手机逐屏截图并保留重叠，结合控件信息、条目身份和图像对齐合成长图；固定搜索栏只在派生长图中去重复。网页先完成目标条目的加载，再判断整页截图、容器截图或分段截图，虚拟列表须另作适配。截图记录开始/结束时间，不宣传为全部内容同一瞬间采集。

**第二层：多关键词汇总图。** 按同一批次、平台、采集端、任务种类和采集配置汇总；顺序取该批次冻结的关键词列表，而非完成先后。APP 与 WEB 共用合成器，但保留各自布局配置。

Pillow 负责画布、等比例排版、留白和输出；OpenCV 仅用于连续滚动帧的重叠对齐辅助，需处理动画和重复封面造成的误匹配。[Pillow 图像接口](https://pillow.readthedocs.io/en/stable/reference/Image.html)、[OpenCV 模板匹配](https://docs.opencv.org/4.x/d4/dc6/tutorial_py_template_matching.html)

原始屏幕帧、单关键词长图、汇总图分开保存并通过清单关联；历史原始文件不覆盖。此处仅复用以往截图工作的原图/派生图分离经验，不代表本项目已有采集实现。

### 清晰度与尺寸

- 搜索结果参考拼图分别为 4792×1753、5001×1592，多关键词长图被明显缩小；这适合总览，不适合作为唯一的文字查看依据。
- 建议保留清晰原图，同时提供横向总览和可配置列数的网格；超过像素/文件大小阈值时输出编号分图。
- 保持宽高比并留白对齐，避免把所有长图强行拉伸为同一高度。总览可压缩，明细图应可放大阅读。
- 部分关键词失败时可先产出明确标注缺失的预览，但“整组完成”仅在满足约定条件后成立；补齐生成新版本，不静默混入上一批图片。

## 5. 字段化目录和文件名

### 数据模型先于目录

内部区分 `platform`、`client`、`capture_kind`：其中 `client=APP/WEB`，`capture_kind=results/suggestions`。用户要求的三个 T 值作为 `display_type` 展示：下拉词、移动端、WEB端。

仅以 T 分组会把手机和网页下拉词混在一起。默认拼图键建议包含：

`(plan_id, batch_id, platform, client, capture_kind, capture_profile_id)`

其中采集配置快照记录会话、排序、N、视口、适配器版本和关键词成员。关键词 ID 不进入多关键词拼图键，原图再关联 `keyword_id` 和图序号。若选择严格实际日期归档，则在此基础上加入实际采集日期分区。

### 建议字段

| 字段示例 | 说明 |
| --- | --- |
| `{year}` | 年，建议提供以防跨年重名 |
| `{month}` / `{month:02d}` | 月份数字 / 至少两位补零月份，对应 m/M |
| `{day:02d}` | 两位日期，对应 D |
| `{platform}` | 平台名，对应 P |
| `{client}` | APP / WEB，额外区分两种下拉词 |
| `{display_type}` | 下拉词 / 移动端 / WEB端，对应 T |
| `{top_n}` | TOP N 的 N，对应 num；仅结果任务适用 |
| `{batch:02d}` | 批次显示序号，对应 n；超过99继续100，不截断 |
| `{keyword}` | 关键词显示值，对应 x，原始搜索词另外完整保存 |
| `{content_label}` | 结果任务如 TOP20，下拉词任务如 下拉词 |
| `{capture_stamp}` | 实际截图时间的文件名友好格式 |
| `{artifact_id}` / `{part:02d}` | 防重标识 / 分图编号 |

界面提供字段按钮、普通文本输入及即时预览；用户不用背变量名。路径和文件名分开配置，原图/拼图各一套模板。以下仅为设计示例，不是已生成目录：

```text
原图导出根目录：H:\搜索截图导出
相对目录模板：{project}-SEO-{month}月平台\{project}-{month}月-{platform}\{month:02d}{day:02d}-{display_type}-{client}\{keyword}
文件名模板：{keyword}_{content_label}_{batch:02d}_{capture_stamp}_{artifact_id}.png

拼图导出根目录：H:\搜索截图导出
相对目录模板：{project}-SEO-{month}月平台\{project}-{month}月-{platform}\{month:02d}{day:02d}-{display_type}-{client}\汇总
文件名模板：{platform}_{client}_{content_label}_{batch:02d}_汇总_{part:02d}_{artifact_id}.jpg
```

关键约束：

- 归档/拼图从数据库与批次清单查询精确字段；不通过“文件路径包含 A1”识别关键词。A1 和 A10 使用不同稳定 ID。
- 月份先是类型化日期数据，9 与 09 只是显示格式；不把月份字符串替换扩散到普通文本。
- `scheduled_at`、`captured_at`、`exported_at` 分开记录。原图日期建议按实际截图时间，重导出仍沿用原截图时间。
- 跨月批次需确认口径：严格实际月份归档时按实际日期拆分汇总；若要求整批按计划月份归档，应使用明确的计划日期字段并显示实际采集区间。避免不经确认就把10月实拍记成9月。
- 关键词中的非法字符、保留名、尾随点/空格、大小写或截断造成的撞名必须检测；显示名清洗不改变实际搜索词，冲突使用稳定短标识消歧。
- 模板预览全批次目标路径，检查原图/拼图重名、目录长度、磁盘空间；拒绝越出所选根目录的路径片段。建议原子写入与内容校验，成功后登记产物。
- 展示路径省略字段不等于丢掉业务身份；若导致覆盖则在运行前报错，不按模糊匹配迁就目录。

## 6. 定时运行与运行架构

“9—21时”只确定范围，还没有确定频率、是否含端点。建议支持每日固定时点、时间窗口内固定间隔、多个窗口、单次日期时间和手动执行；界面预览实际触发点。

- 默认时区 Asia/Shanghai；每日 09:00 至 21:00、每小时一次且含两端时才是 13 批。
- 批次序号建议按计划、按天显示，内部 batch_id 独立且固定；重试沿用批次、增加 attempt，手动新采集创建新批次。
- 调度触发先落库，冻结关键词和模板版本，再排入设备/浏览器队列。调度幂等键覆盖计划、计划版本和触发点，避免程序重启重复建批。
- 采集工作在独立进程运行，管理窗口不承担长时间阻塞。关闭管理窗口是否继续工作需要显式配置；首版可为登录后的后台工作进程，不把有界面浏览器直接塞进 Windows Session 0 服务。
- 任务状态至少区分待执行、执行中、成功、不足N、等待人工处理、失败、超时/错过窗口；拼图另有完整/部分状态。
- 原图抓取重试会产生新的实际时间；错过的历史时点只记录错过或明确标记迟到采集，历史搜索画面无法靠事后补跑重建。
- 同设备严格串行；上一批未完成时下一批如何排队、过期、跳过，应显式配置，避免无限积压。重叠时间窗口需要明确定义是否合并重复触发。
- 系统睡眠、关机、模拟器实例退出/挂起、ADB失联会影响自动运行；窗口最小化是否继续渲染按实际模拟器验证，不承诺无条件无人值守。

APScheduler 提供并发实例限制、错过触发和合并触发等能力；业务完整性和截图时间真实性仍由项目自身实现。[APScheduler 调度语义](https://apscheduler.readthedocs.io/en/3.x/userguide.html)

吞吐估算用实测而非承诺：K 个关键词全部启用8种组合时，每批是 8K 个逻辑截图结果，滚动原始帧和拼图数量另计；按上述13批设置则每日104K个。设备数、耗时和磁盘量均在 PoC 中测量。

## 7. 推荐验证顺序与未定事项

1. **先验证最高风险链路，不先做完整界面。** 在 Android 模拟器内安装两个平台的正式 App，各选少量关键词验证输入、下拉词、TOP N 条目身份、长图连续性；同步测试两平台 WEB 对应能力，覆盖全部8种组合，全程不使用真机。
2. **用真实图片验收。** 检查搜索框关键词一致、顺序/计数可解释、图片加载、接缝无重复或遗漏、截图时间与清单一致；不足N和空下拉结果应有明确记录。
3. **测耗时与稳定性。** 在拟用设备、会话和频率下跑代表性批次，记录成功率、失败原因、耗时分布、输出尺寸，不凭库的存在保证整点批次能完成。
4. **再实现共用模块。** 配置/批次数据库、精确模板导出、分组拼图和调度恢复；至少覆盖 A1/A10、9/10月、跨月、非法字符撞名、APP/WEB下拉词混组、部分失败与重试防覆盖测试。
5. **最后补齐桌面界面与打包。** 在目标 Windows 机器检验 EXE、浏览器、ADB 和手机端依赖，不把构建完成等同于运行验收。[PyInstaller 打包说明](https://pyinstaller.org/en/stable/operating-mode.html)

已定的执行约束：开发和测试不使用真机，采用 Android 模拟器内原生 App。待确认项：单人本地或多人远程管理；每日频率和自定义窗口；TOP N 计数/排序；严格实际日期还是计划批次归档；关键词规模、模拟器实例容量、拼图清晰度与分图接受程度。

本轮协作：主智能体核对资料与技术文档并集成建议；子智能体只读审查导出/调度语义，识别采集端混组、清洗撞名、批次时间与并行冲突。其“计划日期统一归档”建议保留为待确认方案，未作为用户已定规则。
